## Методика

Каждый модуль сверен по трём источникам:
1. Текст даташита (прислан пользователем по частям, этот документ — его систематизация).
2. Реальный установленный HAL (`~/.platformio/packages/framework-mik32v2-sdk/hal/peripherals/Include/`) —
   не вендорный снэпшот в `docs/examples/`, который может быть устаревшим
   ([[feedback_hal_snapshot_vs_installed]]).
3. Текущая реализация конфигуратора: `schemas/*.json`, `parser/<модуль>/`, `codegen/project/*_contribution.cpp`, `gui/peripheral_tree.cpp`.

Статус "HAL есть" означает: закрываемый пробел — есть на что опереться в вендорном коде.
Статус "HAL нет" означает: регистровая работа без HAL-обвязки — заметно дороже и рискованнее,
обязательно требует отдельного проектирования и отдельной HW-валидации
([[feedback_hardware_validation_gate]]).

## Тир 1 — доработка существующих модулей конфигуратора

### USART — ✅ закрыто этой сессией
MSB/LSB, sync-режим, half-duplex, инверсии TX/RX, swap, RTS-режим, модемные
сигналы, DMA. См. `OVERNIGHT_SESSION_REPORT.md`.

#### USART + GPIO — HW-валидация всех 8 `baud_rate`, подтверждено на железе 2026-10-14
8 прошивок (`generated_projects/HWRUN_GPIO_UART_<baud>`) на 1T Rex Board —
UART_0 + GPIO_2 pin 6 toggle, по одной на каждое значение `baud_rate` из
`schemas/uart.json` (9600/19200/38400/57600/115200/230400/460800/921600).
Метод — serial capture через pyserial на `/dev/ttyUSB0` для UART
(чистый текст без искажений на всех 8 скоростях) + визуальное наблюдение
(видимое мигание встроенного светодиода) и мультиметр на `PORT2_6` для
самого GPIO-toggle (подтверждает `docs/implementations/gpio.md`,
раздел 10). **GPIO итог: HW-подтверждён 2026-10-14**, output/toggle на
GPIO_2 pin 6 полностью подтверждён. Баг не найден, регрессий нет. Ранее
(разделы 6-7 `docs/implementations/uart.md`) был проверен только один baud
(38400) — теперь закрыт весь enum.

требований по I2C не содержит — схема построена по HAL.

- ~~Второй собственный адрес + маска~~ (`DualAddressMode`/`OwnAddress2`/`OwnAddress2Mask`) — закрыто (`dual_address_enabled`/`own_address_2`/`own_address_2_mask`, только 7-битный основной адрес).

- ~~Clock stretching~~ (`NoStretchMode`) — закрыто (`no_stretch_mode`), с явным предупреждением в кодогене про недозагрузку TXDR без прерываний/DMA (Errata п.4.1).
- ~~Аналоговый + цифровой фильтр помех~~ (`AnalogFilter`/`DigitalFilter`) — закрыто (`analog_filter`/`digital_filter`, общие для master/slave).

#### I2C — HW-подтверждён 2026-10-14, реальный slave найден на 0x29
`generated_projects/HWRUN_I2C_SCANNER` (I2C_0 master, `clock_speed=100000`,

проверяет NACK, и `Timeout` у `HAL_I2C_*` — число итераций опроса, не

аппаратная проверка — ВЫПОЛНЕНА»). Регрессий нет.

### Timer32 — 🟡 частично закрыто этой сессией, HW-подтверждено
- ~~Выбор источника тактирования~~ — HAL даёт 6 вариантов (`HAL_TIMER32_SourceTypeDef`),
  закрыто необязательным полем `clock_source` (`prescaler`/`tim1_sys_clk`/`tim1_hclk`/
  `tim2_osc32k`/`tim2_lsi32k`/`tx_pad`, default `prescaler` — старое поведение без
  изменений). **Уточнение по ходу работы:** регистр `TIMER_CFG.MUX_TIM32_x` (который
  этот же список исходно называл отдельным нерешённым пунктом) НЕ регистровая
  работа без HAL — `HAL_Timer32_Source_Set` пишет его сама и вызывается внутри
  `HAL_Timer32_Init` (`mik32_hal_timer32.c:80`). Поэтому выбор источника и MUX —
  одна и та же задача, закрытая одним полем, а не два отдельных пункта.
- ~~Маскирование прерываний по типам~~ — добавлены `overflow_interrupt`/
  `underflow_interrupt` (`TIMER32_INT_OVERFLOW_M`/`UNDERFLOW_M`), общие для
  любого instance независимо от набора каналов. Раньше у «голого» счётчика
  (без каналов) не было вообще способа включить прерывание — кодоген жёстко
  звал `HAL_Timer32_Start` (не `_IT`). Теперь при `overflow_interrupt=true`
  (или `underflow_interrupt=true`) используется `HAL_Timer32_Start_IT` и
  генерируется шаблон обработчика, как и для каналов. При каналах — доп.
  маски добавляются отдельным вызовом `HAL_Timer32_InterruptMask_Set` после
  обычного `*_Start_IT` канала (аддитивно, `|=`).

#### Timer32 — HW-валидация (эта сессия, 2026-10-14)
`generated_projects/HW_TEST_TIMER32_IRQ` — Timer32_0, `clock_source=tim1_hclk`,
`overflow_interrupt=true`, prescaler/top подобраны на счётную частоту 10Гц и
период переполнения 1с. Прошито на 1T Rex Board через `/dev/ttyUSB0`, в ручном
`main.c` (`HAL_Init()` + `HAL_EPIC_MaskLevelSet(HAL_EPIC_TIMER32_0_MASK)` — тот
же паттерн, что у SPI HW-теста, см. [[feedback_hal_init_epic_clock_gotcha]]).

Результат: прерывание реально доходит до ядра и печатает счётчик в UART —
`clock_source=tim1_hclk` и маска `overflow_interrupt` подтверждены рабочими.
**Побочная находка:** за 8 секунд напечаталось 72 переполнения вместо
ожидаемых ~8 (период 1с) — то есть обработчик реально входит повторно ~9
раз за один логический период. Это не баг нового кода, а живое подтверждение
уже задокументированной Errata п.9.1 (см. `kErrata91Comment` в
`timer32_contribution.cpp`): «сброс флагов происходит в конце счёта таймера,
во время которого была запись в `INT_CLEAR` — возможен повторный вход в
обработчик прерывания при низкой частоте счёта» — ровно наш случай (10Гц).
**Закрыто (2026-10-14, позже той же сессии):** полный обход реализован в
`timer32_contribution.cpp` (`buildErrata91IrqTemplate`) буквально по
примеру из errata — `TIMER32_<n>_IRQHandler_Template()` отключает маску и
сбрасывает флаг ТОЛЬКО сработавшего источника (не все разом), а новая
`TIMER32_<n>_ReenableAfterErrata91_Template()` — отдельный шаблон для
вызова из основного цикла пользователя, включающий источник обратно,
только когда его флаг реально читается нулём. Каждый канал (compare/
capture) и overflow/underflow считаются независимыми источниками; ШИМ-канал
делит один и тот же `TIMER32_INT_OVERFLOW_M` с `overflow_interrupt` и не
дублируется в списке. Host-side тесты: `ProjectCodegen.Timer32Errata91WorkaroundHandlesTwoIndependentSources`
(два источника одновременно) + обновлённый `Timer32ChannelConfigEmitsErrataWarningAndIrqTemplate`.
HW-подтверждение самого факта повторного входа — см. выше (72 входа/8с);
повторная HW-проверка именно с обходом (убедиться, что реальных обработок
стало ~8, а не 72) не проводилась — требует новой прошивки и доступа к
плате, которая на момент этой правки не отвечает (см. раздел EEPROM).
Сама маска и `Clock.Source` работают верно независимо от обхода: 72 входа
за 8с ≈ 9 входов на логический период — порядок величины ожидаемый от
errata (не 100x и не 0.1x), то есть базовая частота счёта верна, а лишние
входы были именно повторным входом в обработчик, а не неверным prescaler/top.

#### Timer32 — ШИМ `duty_percent` HW-подтверждён 2026-10-14, инверсия проверена явно (не предположена по аналогии с Timer16)
По итогам найденного в этой же сессии бага инверсии CMP/ARR у Timer16 (см.
ниже) Timer32 **намеренно проверен отдельно на реальной плате**, а не
предположен "раз один таймер инвертирован — наверное, и этот тоже": у
Timer16 и Timer32 разные регистровые блоки, перенос вывода без проверки
запрещён (см. память `feedback_no_invented_register_bit_polarity`).

`generated_projects/HWRUN_TIMER32_PWM` — `TIMER32_1` канал 0, `mode=pwm`,
`frequency_hz=1000`, `duty_percent=25`, без `pwm_invert`. Кодоген дал
`top=31999`/`OCR=8000` (прямая формула `ocr=round((top+1)*duty_percent/100)`,
не менялась). Вывод `GPIO_0/PIN_0`. Пользователь измерил мультиметром
**0.82В на GPIO_0.0 при Vcc≈3.3В** — точно 25% **без инверсии**
(`OCR/(top+1)` напрямую, в отличие от Timer16, где было наоборот). Кодоген
Timer32 для `duty_percent` подтверждён корректным как есть, фикс не
требуется.

### Timer16 — частично закрыто этой сессией
- ~~Выбор источника тактирования~~ — HAL даёт 7 вариантов (из них `EXTERNAL_INPUT1` уже
  покрыт полем `mode="external_event_count"`) — закрыто для оставшихся 6
  (`clock_source`: internal_system/ahb/osc32m/hsi32m/osc32k/lsi32k). Частота ШИМ в
  комментарии кодогена вычисляется только для трёх вариантов, совпадающих с
  sys_clk=32МГц по умолчанию (system/ahb/hsi32m) — для osc32m/osc32k/lsi32k
  реальная частота не зафиксирована датащитом/HAL (внешний кристалл или
  некалиброванный RC), поэтому не вычисляется, а не выдумывается.
- ~~Триггер по фронту~~ — хардкод `SOFTWARE` → закрыто (`trigger_edge`: software/rising/falling/both). `Trigger.Source` (8 вариантов GPIO/термосенсор/АЦП/RTC/будильник) остаётся дефолтным — отдельная, более крупная задача.
- ~~Цифровой фильтр помех~~ — хардкод `NONE` → закрыто для обоих фильтров (`external_clock_filter`, `trigger_filter`).
- ~~Режим энкодера/декодера~~ — **закрыто этой сессией (2026-10-14), HW-подтверждено.** Первоначальный вывод "нужны свои пины, регистровая работа без HAL-обвязки, риск сопоставим с Тир 2" оказался неверным — `HAL_TIMER16_MspInit` сама настраивает оба входа Input1/Input2 как `HAL_GPIO_MODE_TIMER_SERIAL`, когда `EncoderMode==ENABLE` (`mik32_hal_timer16.c`: `GPIO_PIN_5|6` для Timer16_0, `8|9` для Timer16_1, `11|12` для Timer16_2). Пины подтверждены ДВАЖДЫ независимо: прямым чтением HAL-исходника и таблицей 193 датащита (`mik32_datasheet_v2_2_3.pdf`, стр.322, пины 45/46/48/49/50/53) — совпали. Новое значение `mode="encoder"` у Timer16 (`schemas/timer16.json`, `parser/timer16/`, `codegen/project/timer16_contribution.cpp`): требует `prescaler=1` (датащит, раздел «Режим энкодера», стр.129 — обязательное условие PRESC[2:0]=0b000) и внутренний источник тактирования (автоматически — `mode="encoder"` никогда не ставит `EXTERNAL_INPUT1`). `HAL_Timer16_Encoder_Start(handle, arr)` вызывается вместо `StartPWM`/`Counter_Start`. Попутно закрыт скрытый пробел конфликт-детекта: пин Input1 (используется и `external_event_count`, и `encoder`) никогда не резервировался в `cross_module_validator` до этой сессии.
- ~~PWM-полярность/инверсия~~ (`Waveform.Polarity`) — хардкод `NONINVERTED` → закрыто (`waveform_inverted`).
- ~~`TIMER_CFG.MUX_TIM16_x`~~ — **исправление аудита (2026-10-14): уже закрыто, оказалось ложным пробелом.** Первоначальный вывод "регистровая работа без HAL-обвязки" был неверным — `HAL_Timer16_SetSourceClock` (вызывается автоматически внутри `HAL_Timer16_ClockInit` → `HAL_Timer16_Init`, `mik32_hal_timer16.c:161-194/513-519`) сама пишет `PM->TIMER_CFG` (регистр `MUX_TIM16_x`) для внутренних источников. Поле `clock_source`, уже реализованное и HW-подтверждённое в прошлой сессии, автоматически закрывает и этот пункт — отдельной доработки не требовалось. Тот же паттерн ошибки, что был в первоначальном выводе по Timer32 (см. раздел Timer32 выше).

#### Timer16 — 🔴 баг найден и исправлен 2026-10-14, HW-подтверждён повторно после фикса
`frequency_hz`/`duty_percent` (добавлено в ночную сессию 12→13.10.2026,
`OVERNIGHT_FIELD_REFERENCE.md`) считало `cmp = period_ticks * duty_percent / 100`
напрямую — но реальное железо работает наоборот: высокий уровень держится
`(ARR−CMP+1)` тактов из `(ARR+1)` (уже задокументировано в
`docs/implementations/timer16.md`, двухточечный мультиметр-тест от
2026-09-06). Новая фича никогда не была сверена с этим фактом и получилась
инвертированной.

Поймано на `generated_projects/HWRUN_TIMER16_PWM` (`frequency_hz=1000`,
`duty_percent=25`, `GPIO_0.7`): кодоген выдал `CMP=8000`/`ARR=31999`,
мультиметр показал **2.48В** (≈75% от `Vcc≈3.2В`) — ровно инверсия
запрошенных 25%.

Исправлено: `parser/timer16/timer16_parser.cpp` (~строка 254-255) —
`cmp_value = period_ticks - round(period_ticks * duty_percent / 100)`;
`codegen/project/timer16_contribution.cpp` (~строка 122) — комментарий
"получилось X%" тоже считал напрямую, исправлен на `(arr+1-cmp)/(arr+1)`.

После фикса тот же конфиг дал `CMP=24000`/`ARR=31999`, пересобрано и
перепрошито — мультиметр показал **0.8В**, точное совпадение с ожидаемыми
25% от ~3.2В. `tests/test_parsers.cpp` (`Timer16FrequencyDuty`,
`duty_percent=50` — симметричная точка) баг не ловил и продолжает проходить
без изменений; несимметричный fixture (например, `duty_percent=25`) для
закрытия этого направления регрессионным тестом пока не добавлен.

#### Timer16 — HW-валидация режима энкодера (эта сессия, 2026-10-14)
`generated_projects/HW_TEST_TIMER16_ENCODER` — UART_0 + Timer16_1, `mode=encoder`,
`prescaler=1`, `arr=65535`. Ручной тестовый `main.c` печатает `CNT`/регистр `ISR`
каждую секунду через `/dev/ttyUSB0`.

Результат: прошивка стабильно работает 8+ секунд без зависаний/сбоев, UART и
Timer16 в режиме энкодера работают одновременно без конфликтов, `ISR=0x01`
(флаг `CMPM` — логично: `CNT`=`CMP`=0 на старте, не ошибка), `CNT` стабильно
0 (без спонтанного дребезга на не подключённых входах — пины корректно
сконфигурированы, а не оставлены в произвольном состоянии).

**Что НЕ проверено:** реальная квадратурная расшифровка (направление/счёт по

прошивку и не конфликтует с остальной периферией.

#### SPI — HW-валидация (эта сессия, 2026-10-13)
Плата: 1T Rex Board, uploader через `/dev/ttyUSB0`
(`elbear_uploader.py`, `platformio.ini` env `development-board-bootloader`).

Собран тестовый проект `generated_projects/HW_TEST_SPI_IRQ` (UART_0 + SPI_0
master, `manual_cs=true`, все 4 поддерживаемых прерывания включены). В ручном
тестовом `main.c` (не часть кодогена — только для этой проверки) добавлен
цикл `HAL_SPI_Exchange_IT` + `trap_handler`, вывод результата в UART0.

**Найдена и исправлена реальная ошибка в самом тестовом коде, не в кодогене:**
без вызова `HAL_Init()` (который включает тактирование EPIC через
`__HAL_PCC_EPIC_CLK_ENABLE` в `HAL_MspInit`) прерывание от SPI физически не
доходило до ядра — счётчик входов в `trap_handler` оставался 0 после ~1 млн
итераций главного цикла. Добавление `HAL_Init()` перед `HAL_EPIC_MaskLevelSet`
исправило это немедленно. Это ценная находка для документации кодогена:
генератор не вызывает `HAL_Init()` сам (как и раньше, EPIC/прерывания — на
стороне пользователя), но теперь это явно подтверждено на железе как
обязательный шаг для любой периферии с прерываниями через EPIC, а не только
предположение из комментариев кода.

После фикса: 8 обменов подряд (~8 секунд), каждый успешно завершается через
IRQ-путь (`HAL_SPI_STATE_END` достигнут во всех 8 случаях), без единого захода
в `HAL_SPI_STATE_ERROR` (OVR/MODF не сработали ни разу), прошивка не зависает.
Результат наблюдался напрямую через `/dev/ttyUSB0` (pyserial, 38400 8N1).

**Что НЕ проверено и остаётся открытым:** реальная корректность данных на
линии (MISO не был физически замкнут на внешний slave или на MOSI —
`input[19]` стабильно `0x00`, т.е. содержимое RX ожидаемо мусорное/плавающее).
Для полной протокольной проверки (клок на SCK, фронты данных на MOSI/MISO,
соответствие `TIMINGR`/`baud_rate_div` реальной частоте) нужен логический
анализатор на выводах SPI0_SCK/MOSI/MISO/SS — не было физической прошивки
второй платы в роли slave в этой сессии. То, что проверено железно: сам
факт, что прерывание реально взводится, доходит до ядра, обрабатывается
сгенерированным `SPI_0_IRQHandler_Template()` и корректно переводит обмен в
`HAL_SPI_STATE_END`, а не зависает/не падает в `ERROR` — то есть именно тот
риск, из-за которого прерывания раньше не были реализованы (неверная
маска/порядок включения), снят.

#### SPI — поллинг-режим HW-подтверждён 2026-10-14
У пользователя нет SPI-датчиков — цель проверки: убедиться, что без slave
на шине ничего не виснет и вывод чистый. `generated_projects/HWRUN_SPI_POLL`
(SPI_0 master, `manual_cs=false`, блокирующий `HAL_SPI_Exchange`, без
прерываний) — 9+ раундов обмена подряд, `status=HAL_OK` каждый раз, `rx`
всегда `0x00` (ожидаемо, MISO не подключён), без единого зависания. Кодоген
для поллинг-режима подтверждён.

**Known issue, НЕ блокирует (не баг кодгена):** повторный
`HAL_SPI_Exchange_IT` при `manual_cs=true` из прикладного цикла вешает плату
намертво начиная со второго обмена (первый проходит успешно). Причина не
установлена до конца — подозрение на то, что HAL не переводит `hspi->State`
в `BUSY` сразу и не чистит TX/RX FIFO между обменами в режиме `manual_cs=true`

(кодоген генерирует только `Init`/`IRQHandler`-шаблон, цикл обмена — на
стороне пользователя), не в `codegen/project/spi_contribution.cpp`.
Рекомендация до дальнейшего расследования: `manual_cs=false` либо
блокирующий `HAL_SPI_Exchange` для нескольких последовательных обменов —
см. `docs/implementations/spi.md`.

#### Clock/PCC — HW-валидация (эта сессия, 2026-10-14)
Три прошивки на 1T Rex Board через `/dev/ttyUSB0`, UART0 печатает тик каждые
2 млн итераций цикла — чистота принятого текста = прокси для точности
фактической частоты ядра:

1. `oscillator_system=osc32m`, `oscillator_enable=[osc32m]` (остальные три
   источника выключены), `force_osc_sys=true` — текст идеально чистый
   (`CLOCK_PCC_TEST osc32m-only, tick=2000000`). Подтверждает: маска
   осцилляторов и `force_osc_sys` работают, можно реально выключить
   неиспользуемые генераторы без потери работоспособности.
2. `oscillator_system=hsi32m`, `oscillator_enable=[hsi32m]`,
   `hsi32m_calibration=128` (дефолт) — текст искажён (нечитаемые байты).
3. То же самое с `hsi32m_calibration=150` — другой паттерн искажений
   (не совпадает с п.2 побайтово), то есть поле реально влияет на частоту,
   просто 150 тоже не попадание в точное значение для этого конкретного
   кристалла.

**Важная находка, не баг:** внутренний RC-генератор HSI32M (в отличие от
внешнего кварца `osc32m`) не даёт точных 32МГц на "паспортном" калибровочном
значении 128 — это ожидаемое поведение не откалиброванного RC-генератора
(разброс параметров между экземплярами кристалла), а не ошибка кодогена.
Правильное калибровочное значение для конкретной платы можно подобрать
только измерением реальной частоты (осциллограф/частотомер на тактовом
выходе) — конфигуратор предоставляет ручку (`hsi32m_calibration`), но не
может угадать нужное значение без измерения на конкретном экземпляре
кристалла. Источники RTC (`rtc_clock_source`/`rtc_clock_cpu_source`) HW не
проверялись отдельно — в конфигураторе ещё нет модуля RTC, который бы
потреблял эту настройку наблюдаемым образом (см. Тир 2, RTC).

### RTC — ✅ закрыто этой сессией (2026-10-14), HW-подтверждено

Первый модуль Тир 2, реализованный с нуля: `schemas/rtc.json`, `parser/rtc/`,
`knowledge_base/rtc.json`, `codegen/project/rtc_contribution.{h,cpp}`. RTC —
единственный глобальный блок (`hrtc.Instance = RTC`, без нумерации 0/1/2,
`mik32_memory_map.h`) — максимум один блок `type="rtc"` на проект.

Текущее время (`time`: день недели/часы/минуты/секунды) и дата (`date`:
век/число/месяц/год, с валидацией дня месяца относительно високосного года —
29 февраля отвергается для невисокосных лет) устанавливаются один раз при
инициализации. Необязательный будильник (`alarm`): сравнивает ПОДМНОЖЕСТВО
полей (`compare_fields`, дефолт — все восемь, как в обоих вендорных примерах)
— например, только `hours`/`minutes`/`seconds` даёт "каждый день в это
время", игнорируя день/месяц/год/день недели. `interrupt_enabled` включает
прерывание и генерирует `RTC_IRQHandler_Template()`.

**Rust-ветка:** RTC явно отвергается (`validation/rust_feature_validator.cpp`)
— `mik32-hal-main` не содержит модуля RTC.

**Ограничение этой сессии:** в `cmake_project_codegen.cpp` (путь
`per_type_files=true` для CMake-тулчейна) RTC не подключён — вклад просто не
попадёт в per-type-файлы при этой конкретной комбинации опций. Основной путь
(PlatformIO, CMake без `per_type_files`) работает полностью. Отдельная,
самостоятельная задача на будущее, не блокирующая этот аудит (CMake и так не
HW-подтверждён как путь, см. CLAUDE.md).

#### RTC — HW-валидация (эта сессия, 2026-10-14) — найдены и исправлены ДВА реальных бага

`generated_projects/HW_TEST_RTC` — UART_0 + RTC (время 23:59:55, будильник
через 10 секунд, пересекающий полночь — проверяет и тиканье, и перенос
даты/дня недели, и будильник одним тестом), 1T Rex Board, `/dev/ttyUSB0`.

**Баг №1 (в самом кодогене, исправлен в `rtc_contribution.cpp`):**
в отличие от Timer16/Timer32, `HAL_RTC_MspInit` НИКОГДА не вызывается
автоматически ни одной функцией `HAL_RTC_*` — оба вендорных примера вызывают
`__HAL_PCC_RTC_CLK_ENABLE()` вручную первой строкой `RTC_Init()`. Кодоген
исходно не вызывал этот макрос — счётчик RTC просто не шёл (регистры не
тактируются). Добавлен вызов `__HAL_PCC_RTC_CLK_ENABLE()` первой строкой
сгенерированной `RTC_Init()`.

**Баг №2 (паттерн для пользователя, закрыт шаблоном обработчика в кодогене):**
`RTC_CTRL.ALRM` — уровневый флаг. Простое `HAL_EPIC_Clear()` в
`raw_trap_handler` его НЕ снимает — без явного `HAL_RTC_ClearAlrmFlag` линия
прерывания остаётся активной, и ядро немедленно уходит в обработчик снова
сразу после `return`, бесконечно, даже не успевая вернуться в `main()`.
Обнаружено дважды за один HW-прогон: (1) при повторной прошивке — RTC (как
WU, отдельный тактовый/питательный домен) переживает reflash в рамках
одного включения питания, и флаг от предыдущего запуска вешал прошивку ещё
до первого `xprintf`; (2) в момент реального срабатывания будильника —
прошивка тикала секунды нормально и зависала точно на границе 00:00:05.
Кодоген теперь генерирует правильный `RTC_IRQHandler_Template()`
(`HAL_RTC_AlarmDisable`+`HAL_RTC_ClearAlrmFlag`), чтобы пользователь не
находил эту проблему сам.

После обоих исправлений: время идёт секунда за секундой, дата/день недели
корректно перешли через полночь (14→15 октября, пт→сб), будильник сработал
ровно в 00:00:05 через реальный прерывание-путь, прошивка не зависла и
продолжила работу. Побочно замечен (не воспроизведён стабильно, не блокирует
закрытие) единичный случай нечитаемого промежуточного значения `GetTime`
прямо на границе полуночи — вероятно, чтение несвязанных BCD-регистров
(часы/минуты/секунды и день недели читаются отдельными полями без
аппаратной синхронизации) застаёт аппаратуру в середине каскадного переноса;
тот же паттерн чтения используется и в вендорных примерах без какой-либо
защиты. Не влияет на корректность самого RTC — проявляется только в отдельных
нечастых кадрах чтения.

**Регрессия после рефакторинга `project_codegen.cpp`/`project_config.cpp`
проверена повторно 2026-10-14, баг не найден.** Перегенерирован
`generated_projects/HWRUN_RTC_REGR` с новым временем/датой/будильником,
перенесён уже проверенный `main.c` — прошито, время считает верно
(`12:00:00` → `12:00:04` за 4 реальных секунды), дата/день недели верны,
структура `mik32_init.c` идентична прежней по форме.

### CRC — ✅ закрыто этой сессией (2026-10-14), HW-подтверждено

Второй модуль Тир 2 с нуля: `schemas/crc.json`, `parser/crc/`,
`codegen/project/crc_contribution.{h,cpp}` (без knowledge_base — у CRC нет
per-instance данных из датащита, оба булевых поля отображаются в ровно два
документированных HAL-макроса каждое напрямую). CRC — единственный
глобальный блок, как и RTC.

Два способа задать алгоритм: явные поля (`poly`/`init`/`input_reverse`/
`output_reverse`/`output_inversion`) либо `preset` — один из девяти
стандартных CRC-32 алгоритмов, перечисленных в `mik32_hal_crc32.h` (строки
240-283: crc32, crc32_bzip2, crc32c, crc32d, crc32_jamcrc, crc32_mpeg2,
crc32_posix, crc32q, crc32_xfer) — взаимоисключающе, тот же приём, что
`frequency_hz`/`prescaler` у Timer16/Timer32. Кодоген только конфигурирует
алгоритм (`HAL_CRC_Init`) — вызовы `HAL_CRC_WriteData`/`WriteData32`/`ReadCRC`
на собственных данных пользователя остаются за пользователем, угадать их
наперёд невозможно.

Rust-ветка явно отвергает CRC (`validation/rust_feature_validator.cpp`) —
`mik32-hal-main` не содержит модуля CRC.

#### CRC — HW-валидация (эта сессия, 2026-10-14)

`generated_projects/HW_TEST_CRC` — UART_0 + CRC (`preset=crc32q`), 1T Rex
Board, `/dev/ttyUSB0`. Использованы контрольные значения прямо из вендорного
примера `docs/examples/mik32-examples/HAL_CRC32/src/main.c` (тот же алгоритм,
те же тестовые данные) — не выдуманные числа.

Результат: оба контрольных значения совпали побитово с первой попытки —
CRC от байт `"123456789"` дал `0x3010BF7F` (ожидалось то же), CRC от слов
`{0xABCDABCD, 0xA1B2C3D4}` дал `0x6311BC18` (ожидалось то же). Никаких
доработок не потребовалось — в отличие от RTC, `HAL_CRC_Init` сама вызывает
`HAL_CRC32_MspInit` (включает тактирование), поэтому класс ошибки
"забыли включить тактирование периферии" здесь не воспроизвёлся.

**Регрессия после рефакторинга `project_codegen.cpp`/`project_config.cpp`
проверена повторно 2026-10-14, баг не найден.** Перегенерирован
`generated_projects/HWRUN_CRC_REGR` (`preset=crc32q`), перенесён уже
проверенный `main.c` — прошито, оба значения снова совпали (bytes
`0x3010BF7F` match=1, words `0x6311BC18` match=1), структура
`mik32_init.c` идентична прежней по форме.

### TSENS (датчик температуры) — ✅ HW-подтверждён 2026-10-14

`schemas/tsens.json`, `parser/tsens/`, `codegen/project/tsens_contribution.{h,cpp}`
— единственный глобальный блок (`TSENS_HandleTypeDef.Instance = ANALOG_REG`),
как DAC/ADC/CRC/RTC. `clock_source` (6 вариантов)/`frequency_hz` (1-100000,
ограничение HAL "не больше 100кГц")/опциональные пороги
`low_threshold_celsius`/`high_threshold_celsius` (-40..125)/опциональные
`interrupts` (`low`/`high`/`eoc`). Кодоген генерирует только `TSENS_Init` —
`HAL_TSENS_SingleStart`/`ContinuousStart` остаются за пользователем.

`generated_projects/HWRUN_TSENS` (`clock_source=hsi32m`, `frequency_hz=40000`)
прошит на 1T Rex Board — `HAL_TSENS_SingleStart` (вызван вручную в тестовом
коде) дал `status=HAL_OK`, `temp=33.75°C` — правдоподобное значение для
платы комнатной температуры. Баг в кодгене/схеме не найден.

**Предостережение для ручных тестов (не баг кодгена, тот же класс, что уже
встречался у I2C):** первая попытка с `Timeout=100000` дала
`statusHAL=HAL_TIMEOUT`. `Timeout` у `HAL_TSENS_*` (как и у `HAL_I2C_*`) —
число итераций busy-wait цикла, не миллисекунды; 100000 было мало для
реального времени АЦП-преобразования термосенсора. С `Timeout=10000000`
получен `HAL_OK`. См. `docs/implementations/tsens.md`.

### OTP — ✅ HW-подтверждён 2026-10-14, read-only (последний пункт "рискованной тройки")

**Итог: HW-подтверждён 2026-10-14, read-only (оба режима `read_mode`),

### EEPROM-контроллер — 🔴 ВТОРОЙ инцидент на этом модуле, плата сейчас НЕ ОТВЕЧАЕТ (2026-10-14)

Третий модуль Тир 2: `schemas/eeprom.json`, `parser/eeprom/`,
`codegen/project/eeprom_contribution.{h,cpp}` — та же схема, что у RTC/CRC
(единственный глобальный блок, конфигурация без knowledge_base). Поля:
`mode` (`two_stage`/`three_stage`), `ecc_enabled`, `single_error_interrupt_enabled`.
Кодоген вызывает `HAL_EEPROM_Init` + `HAL_EEPROM_CalculateTimings(32000000)` —
`HAL_EEPROM_Erase/Write/Read` на произвольных адресах/данных остаются за
пользователем. В отличие от `HAL_RTC_Init`, ни `HAL_EEPROM_Init`, ни сам
вендорный пример не вызывают явно `__HAL_PCC_EEPROM_CLK_ENABLE()` — решено
доверять реальному коду (CLAUDE.md), не добавлять вызов, которого нет даже в
проверенном примере. Rust-ветка явно отвергает EEPROM.

#### EEPROM — reverse-import маппер добавлен 2026-10-18 (парсер, НЕ прошивка)

`parser/reverse_import/eeprom_reverse_mapper.{h,cpp}` — по образцу
`crypto_reverse_mapper.cpp` (глобальный блок, синтетический `instance=0`),
на основе `docs/examples/mik32-examples/HAL_EEPROM/src/main.c:237-246`:
`mode` (обязательное, `HAL_EEPROM_MODE_TWO_STAGE`/`THREE_STAGE`),
`ecc_enabled`/`single_error_interrupt_enabled` (опциональные, дефолты схемы
true/false). Тесты — `tests/test_reverse_import_eeprom.cpp`, 370/370 зелёные.

Это НЕ противоречит запрету на HW-тесты EEPROM — reverse-import ничего не
прошивает и не выполняет на плате, только разбирает существующий текст
C-файла в JSON (см. преамбулу раздела «Reverse-import» выше). Статус самого
forward-кодогена EEPROM (🔴, HW-валидация запрещена) не меняется.

#### Инцидент №1 (ранее в этой же сессии, 2026-10-14)

Собран `generated_projects/HW_TEST_EEPROM` (тест 1-в-1 по вендорному
примеру `HAL_EEPROM/src/main.c`: запись `0x55555555`×32 слова во все
страницы + возрастающий паттерн в одну страницу, оба со сверкой чтением).
После прошивки и одного неудачного прогона чтения плата перестала отвечать
на протокол загрузчика (`Device not responding`) и не восстановилась ни
после нескольких переподключений USB/сброса DTR. Не было установлено,
вызвано ли это зависанием самой прошивки (например, в `HAL_EEPROM_WaitBusy`)
или физической причиной, не связанной с этим кодом. Дальнейшие попытки
прошивки были намеренно приостановлены.

**Промежуточное восстановление:** позже в середине сессии неразрушающий
bootloader-пробник (`package_size` handshake без прошивки) показал `ACK` —
плата временно восстановилась сама (вероятно от переподключения/времени).

#### Инцидент №2 — "полный тест" по осознанному выбору пользователя, плата снова не отвечает

Пользователь явно выбрал повторить полный EEPROM-тест с осознанием риска.

**Тестовый код (отличался от инцидента №1):** `generated_projects/HWRUN_EEPROM`
(`mode=two_stage`, `ecc_enabled=true`). В `main.c` — **тот же** тест, что
вызвал первый инцидент (Erase `WRITE_ALL` → Write `0x55555555`×32 → Read;
затем Erase `WRITE_SINGLE` → Write возрастающий паттерн → Read), но с двумя
изменениями, нацеленными против подозреваемого класса бага:
1. `EEPROM_OP_TIMEOUT` увеличен со `100000` до `50000000` — подозревался
   тот же класс бага, что был успешно найден и исправлен этой же сессией в
   I2C/TSENS (`Timeout` — счётчик итераций busy-wait, не миллисекунды).
2. Явная проверка HAL-статуса после каждого Erase/Write/Read, с остановкой
   на первом `HAL_TIMEOUT`, вместо слепого продолжения без проверки.

Собрано, прошито (`"Uploaded successfully"`) — и **ни одной строки не
пришло по UART**, даже стартовый баннер до любых EEPROM-операций вообще.

**Поправка к собственному первоначальному выводу, важно для следующей
сессии:** сначала предположено, что зависание — в `EEPROM_Init()`/
`HAL_EEPROM_CalculateTimings()`. Проверка реального кода этих функций
(`templates/mik32_sdk_snapshot/hal/peripherals/Source/mik32_hal_eeprom.c`)
показала: **там нет ни одного цикла/ожидания** — чистые регистровые записи
и арифметика, зависнуть физически на этом невозможно. Значит исходный
диагноз был неверным. **В отличие от успешных находок этой же сессии
(I2C/TSENS/Timer16, где теория "Timeout — счётчик итераций" подтвердилась и
решила проблему), для EEPROM эта теория НЕ объясняет происходящее** —
реальная причина зависания/отказа **не установлена**. Кандидаты:
(а) повреждённая/неполная прошивка SPIFI при аплоуде, несмотря на
сообщение `"Uploaded successfully"`; (б) что-то иное, затрагивающее весь
чип, не только EEPROM-путь.

**Диагностика после прошивки, все попытки безрезультатны:**
- Bootloader-пробник (`package_size` handshake, без прошивки) —
  `NO_RESPONSE`, 5+ попыток подряд.
- Физическое переподключение USB (устройство переехало на новый номер в
  `lsusb`) — пробник всё равно `NO_RESPONSE`.
- Перебраны все 4 комбинации 2 DIP-переключателей (предполагаемый выбор
  `BOOT_EEPROM`/`BOOT_RAM`/`BOOT_SPIFI`, `shared/periphery/boot.h`), с
  нажатием Reset между каждой комбинацией — ни одна не восстановила
  отклик загрузчика.
- Подтверждено пользователем: **upload-протокол (`elbear_uploader.py`)
  тоже не проходит**, не только диагностический пробник — "сейчас даже
  прошить другой прошивкой не могу".

**Статус на конец сессии: плата НЕ ОТВЕЧАЕТ.** По решению пользователя —
дальнейшие программные попытки восстановления прекращены (риск
усугубить). Открытые вопросы для следующей сессии:
1. Нужен JTAG/SWD-отладчик для полного восстановления —
   `platformio.ini` поддерживает `upload_protocol = jlink`/`olimex-*`/
   `sipeed-rv-debugger`/`mikron-development-board` как альтернативы
   `elbear_uploader.py`, но неизвестно, есть ли физически такое
   оборудование.
2. Точное назначение/полярность конкретно этих двух DIP-переключателей на
   1T Rex Board не задокументировано нигде в репозитории — нужна
   распиновка платы (не датащит МК), которой сейчас нет.

**Статус WDT: НЕ ПРОТЕСТИРОВАН** — не успели дойти по плану сессии,
EEPROM-инцидент заблокировал дальнейшую работу с платой раньше, чем
очередь дошла до WDT. См. раздел ниже (статус не изменился со старого
"HW-валидация не начата", но причина теперь — инцидент №2 выше, не только
недоступность по инциденту №1).

### WDT — 🟡 код+тесты готовы, HW-валидация НЕ НАЧАТА (заблокировано инцидентом EEPROM №2, 2026-10-14)

Четвёртый модуль Тир 2: `schemas/wdt.json`, `parser/wdt/`,
`codegen/project/wdt_contribution.{h,cpp}`. Поля: `clock_source`
(osc32m/hsi32m/osc32k/lsi32k) и `reload_ms` (верхняя граница зависит от
источника — 524мс для 32МГц-источников, 511875мс для 32кГц, обе цифры из
`mik32_hal_wdt.h`, проверено в парсере как межполевая зависимость).

**Осознанное решение по безопасности:** кодоген генерирует ТОЛЬКО
`HAL_WDT_Init` — `HAL_WDT_Start`/`HAL_WDT_Refresh` никогда не вызываются
автоматически. Автозапуск сторожевого таймера без гарантии, что
пользовательский `main()` будет регулярно вызывать `HAL_WDT_Refresh`,
привёл бы к безусловному циклическому сбросу платы через `reload_ms` после
первого включения — недопустимое поведение для автогенерируемого кода.
Вендорный пример `HAL_WDT` прямо демонстрирует этот сброс как ожидаемый
результат («программа заходит в бесконечный цикл, в котором таймер
досчитывает до конца и формирует сигнал сброса»).

**HW-валидация не начата** — плата недоступна (см. раздел EEPROM выше);
прошивать WDT-содержащий код на уже не отвечающую плату намеренно не
предпринималось, чтобы не затруднить диагностику дальше.

## Тир 3 — новые модули, HAL нет (регистровая работа, дороже и рискованнее)

Статус на 2026-10-14: реализованы PVD и Bus Watchdog (регистровая запись,
config-only, та же схема safety-паттерна "кодоген настраивает, но не
запускает рискованное действие", что у WDT/OTP). Остальные четыре пункта
(EPIC-generic, Boot Manager, Power modes, VCC/VBAT, Wakeup events)
сознательно отложены — причина у каждого своя, см. ниже таблицу.

| Модуль | Что нужно | Примечание |
|---|---|---|
| ✅ **Монитор питания (PVD, VCC/AVCC)** | пороги `OVER_THRESH`/`UNDER_THRESH`, цифровой фильтр | **Закрыто, HW-подтверждён 2026-10-14.** `schemas/pvd.json`, `parser/pvd/`, `codegen/project/pvd_contribution.cpp`. HAL даёт только `__HAL_PCC_PVD_CONTROL_CLK_ENABLE()` — остальное прямая запись в `PVD_CONTROL->CONFIG/DPF_VALUE` (`shared/periphery/pvd_control.h`). **Сознательно не реализованы** биты `CONFIG.NRESETU/NRESETO` (сброс платы по порогу) — ни в одном доступном материале (HAL, примеры) нет подтверждения полярности этих битов, а угадывание напрямую означает риск необоснованного сброса платы. Кодоген не трогает эти биты вообще (остаются как после reset). `generated_projects/HWRUN_PVD`: `CONFIG=0x00000C31` совпал с ожидаемым `(3<<4)|(12<<8)`, `NRESETU`/`NRESETO` подтверждены нетронутыми (read-modify-write). Находка (не баг): бит `PD` тоже не трогается кодгеном — после сброса PVD физически выключен (`PD=1`), реально включать компаратор оставлено пользователю, см. `docs/implementations/pvd_bus_watchdog.md`. |
| ✅ **Сторожевой таймер шины (Bus Watchdog)** | 3 монитора шины (EEPROM/SPIFI/DOM3) | **Закрыто, HW-подтверждён 2026-10-14 — найден и исправлен опасный баг диапазона.** `schemas/bus_watchdog.json`, `parser/bus_watchdog/`, `codegen/project/bus_watchdog_contribution.cpp`. Нет HAL-обёртки — только `__HAL_PCC_WDT_BUS_CLK_ENABLE()` + прямая запись `WDT_BUS->TIMEOUT/ENABLE` (`shared/periphery/wdt_bus.h`). По умолчанию все три линии выключены (как системный WDT) — пользователь явно включает нужные поля в JSON. Парсер отказывает, если линия включена, а `timeout=0` (сработает немедленно). **Ключевая находка:** `TIMEOUT` оказался реально 4-битным регистром (макс. `15`), а не 32-битным, как было объявлено в старой схеме/`wdt_bus.h` — `timeout=4294967295` считался обратно как `0x0000000F`. Проверка гипотезы `timeout=1000000` (младший нибл `0x0`) обрезала эффективный таймаут линии **DOM3 (шина APB, через неё работает весь чип, включая UART)** до `0` — плата переставала отвечать по UART сразу после прошивки (непрерывный сброс по шине). Восстановлено `timeout=15`. Исправлено: `schemas/bus_watchdog.json` (`timeout.max → 15`) + `parser/bus_watchdog/bus_watchdog_parser.cpp` (диапазон был захардкожен отдельно в C++) + обновлены фикстуры + новый тест `BusWatchdogParse.RejectsTimeoutOutOfRange`. `ctest` 323/323 после фикса. Подробности — `docs/implementations/pvd_bus_watchdog.md`. |
| 🔴 **EPIC / контроллер прерываний (генерик-модуль)** | доп. линии, не покрытые другими модулями: PVD AVCC/VCC, BOR, battery-not-good, freq monitor, DMA global error | **Отложено.** HAL есть (`mik32_hal_irq.h/.c` — `HAL_EPIC_MaskEdgeSet/Clear`, `MaskLevelSet/Clear`, `GetStatus`, `Clear`), но для этих конкретных источников нет документированной классификации edge/level ни в HAL-заголовке, ни в примерах — угадывание воссоздаёт ровно тот класс ошибки, что уже два раза ловился в этой сессии на RTC/EPIC (уровневый флаг, не очищенный правильно → бесконечный повторный вход в прерывание). Каждый существующий модуль (RTC/SPI/Timer16/Timer32/TSENS) уже сам настраивает своё EPIC-маскирование корректно — отдельного стандаартного модуля для "лишних" линий без датащита с таблицей edge/level делать не стали. |
| 🔴 **Boot Manager** | регистр `BOOT`, чтение режима загрузки Boot0/Boot1 | **Отложено как неприменимо.** `shared/periphery/boot.h` — только `#define BOOT_EEPROM/BOOT_RAM/BOOT_SPIFI` и read-only регистр, нет ни HAL, ни семантики "инициализации" — это runtime-запрос состояния, а не настраиваемая периферия. Не подходит под архитектуру "JSON-конфиг → init-функция". |
| 🔴 **Режимы энергопотребления** (`PM->SLEEP_MODE`, тактовые делители AHB/APB) | конфигурация делителей и retention-битов на время сна | **Отложено.** Регистровый блок `PM` — тот же физический блок, которым управляет уже существующий модуль Clock/PCC (`ClockConfig`/`renderSystemClockConfig`, `project_codegen.cpp`). Добавление отдельного Тир-3 модуля поверх него создало бы два независимых источника записи в один и тот же регистровый блок (риск конфликтующих/перезаписывающих друг друга настроек делителей) — правильное место для этого функционала — расширение Clock/PCC в отдельной сессии, не новый модуль. |
| 🔴 **Схема переключения VCC/VBAT** | регистр `WU->POWER_SWITCH` | **Отложено из-за состояния платы.** Нет HAL, чисто регистровая работа — переключение питания backup-домена (от которого зависит RTC/retention). Генерировать и, тем более, советовать пользователю прошивать код, переключающий силовые домены, пока физическая плата не отвечает на bootloader после несвязанного инцидента (см. раздел EEPROM) — неприемлемый риск; при ошибке результат неотличим от уже случившегося "кирпича" и непроверяем до восстановления платы. |
| 🔴 **События пробуждения** (`WU->SYS_MASK/SYS_LEVEL`, вход в `WU->STOP`) | маски/уровни EXT_WU и RTC для выхода из Стоп/Ожидание | **Отложено из-за состояния платы.** Нет HAL. Включение источников пробуждения как таковое не опасно, но настоящая ценность модуля — вход в режим STOP (`WU->STOP`), а это переводит ядро в низкопотребляющий режим с риском не выйти обратно при неверной настройке тактирования/пробуждения — та же причина отложить, что у VCC/VBAT: нельзя проверить на живой плате прямо сейчас. |

## FreeRTOS (межмодульный компонент, не периферия датащита)

### FreeRTOS — ✅ HW-подтверждён 2026-10-14, с найденным и исправленным критичным багом линковки

Первая HW-валидация этого модуля за всю историю проекта (до этой сессии
статус был "HW-валидация ещё не сделана" — ни планировщик, ни IRQ→семафор
не проверялись на реальной плате вовсе).

**Найден критичный баг — не в коде конфигуратора, а в линкер-скрипте
установленного SDK-пакета.** Симптом: любой сгенерированный
FreeRTOS-проект (даже одна задача без семафоров) перезагружался в
бесконечном цикле прямо на первом `vTaskDelay()`. Причина: правило
`KEEP(*(.trap_text))` в
`~/.platformio/packages/framework-mik32v2-sdk/shared/ldscripts/sections.lds`
не ловит именованные ассемблерные подсекции вида
`.trap_text.freertos_risc_v_trap_handler`, которые генерирует
`FreeRTOS-Kernel/portASM.S` (в отличие от остального HAL-кода, кладущего
код в голые секции `.trap_text`/`.ram_text`). Такая секция приземляется у
компоновщика на `VMA=LMA=0x0` — вызов через неё = прыжок в никуда = крах на
первом же прерывании (тик-таймер FreeRTOS). Подтверждено `objdump -h`.

**Фикс** (без модификации системного SDK-пакета — правка файлов вне
каталога проекта заблокирована сознательно): `codegen/project/freertos_codegen.cpp`,
функция `writeFreeRtosKernelSource`, генерирует локальный `spifi.ld` в
корень каждого сгенерированного FreeRTOS-проекта с добавленным правилом
`KEEP(*(.trap_text.*))` — PlatformIO (`mik32 platform
builder/frameworks/custom.py`) ищет `spifi.ld` сначала в `$PROJECT_DIR`,
локальный файл перекрывает баговую глобальную версию.

Подтверждено дважды на 1T Rex Board: (1) одна задача без семафора — тик
стабильно `0→680+` без сбоев; (2) полный сценарий (2 задачи + бинарный
семафор + GPIO toggle + UART лог) — 7+ успешных приёмов семафора подряд.
Также подтверждено, что фикс срабатывает автоматически при обычной
генерации через CLI (независимый третий проект, без единой ручной правки).

Полное описание находки (objdump-доказательство, точное место фикса в
`freertos_codegen.cpp`) — см. `docs/implementations/freertos.md`, раздел
«ПЕРВАЯ HW-валидация — КРИТИЧНЫЙ БАГ НАЙДЕН И ИСПРАВЛЕН 2026-10-14».
Непроверенным остаётся только `vApplicationMallocFailedHook`/
`configCHECK_FOR_STACK_OVERFLOW` (нужен отдельный сценарий с намеренно
урезанным `stack_size_words`).

## Reverse-import (межмодульный компонент, чистый парсер — HW-уровня нет)

### reverse-import — widened-тест на 53 реальных вендорных проектах проведён 2026-10-14, 1 баг найден и исправлен, 1 архитектурное ограничение задокументировано как открытое

HW-уровня у этого модуля нет (чистый парсер, ничего не прошивается) — но
до этой сессии сканер проверялся только против собственных
`generated_projects/*`. Эта сессия прогнала его впервые против **реальных
вендорных примеров**: `importProjectFromDirectory()` вызван напрямую через
временный harness на всех 53 директориях `docs/examples/mik32-examples/*`.
Ни одного падения/зависания/таймаута — главный критерий надёжности пройден.

**Найден и исправлен баг** в `parser/reverse_import/timer16_reverse_mapper.cpp`:
голый `std::stoll(arg)` без базы для hex-литерала `"0xFFFF"` молча парсил
только ведущий `"0"` и возвращал `0` без заметки (найдено на
`docs/examples/mik32-examples/HAL_Timer16/src/main.c:34`). Исправлено новой
`parseIntegerLiteralStrict` (база 0, проверка полного потребления аргумента,
honest-note при неудаче — тот же паттерн, что уже был у
`i2c_reverse_mapper::clock_speed`). SPI/Timer32-канал не затронуты — там уже
стоит строгий regex-гейт.

**Найдено, не исправлено (архитектурное ограничение):** в том же примере
`HAL_Timer16_Init`/`HAL_Timer16_StartPWM` разнесены по разным функциям
(`Timer16_1_Init()` vs `main()`) — сканер ассоциирует "trailing call после
Init" только в пределах одной лексической области (как генерирует сам
конфигуратор), межфункциональная связка не распознаётся. Деградация
graceful (существующий fallback period/0/0 срабатывает корректно, не
крашится и не даёт неверных данных) — полноценный межфункциональный анализ
вызовов отложен как отдельная, более крупная задача.

Подробности — `docs/implementations/reverse_import.md`, раздел «Прогон
против docs/examples/mik32-examples (2026-10-14)».

### reverse-import — мапперы для DAC/CRYPTO/DMA добавлены 2026-10-18

До этой правки у ADC/DAC/CRYPTO/DMA (единственных Тир-2 периферий с готовым
forward-кодогеном) не было ни одного reverse-import-маппера — обратный
разбор существующего C-проекта просто пропускал эти блоки. Добавлены три
новых маппера по образцу `adc_reverse_mapper.cpp` (`parser/reverse_import/
{dac,crypto,dma}_reverse_mapper.{h,cpp}`), с тестами
(`tests/test_reverse_import_{dac,crypto,dma}.cpp`, 365/365 тестов зелёные).

- **DAC** — прямой перенос паттерна ADC: `instance` (0/1, из `Instance_dac`,
  НЕ из всегда-константного `Instance`), `div`/`ext_ref`/`ext_clb`.
- **CRYPTO** — глобальный блок без поля `instance` в схеме (как у RTC/CRC) —
  синтезируется `instance=0` для совпадения с конвенцией GUI-дерева
  (`gui/project_document.cpp::defaultBlock()`), тот же класс фикса, что был
  найден на ADC в прошлой сессии. `swap_mode`/`order_mode` — опциональные
  поля с документированным дефолтом схемы (отсутствие поля — не unresolved,
  это не угаданное значение, а применение схемного дефолта); `algorithm`/
  `cipher_mode` — обязательные (отсутствие → unresolved).
- **DMA (канал)** — потребовал расширения самого сканера
  (`reverse_import_scanner.cpp`): у `DMA_ChannelHandleTypeDef` нет функции
  `HAL_*_Init` в реальном HAL (подтверждено прямым чтением
  `mik32_hal_dma.h` — только `HAL_DMA_Init` для ГЛОБАЛЬНОГО `DMA_InitTypeDef`,
  `HAL_DMA_Wait`, `HAL_DMA_Start`), поэтому блок канала никогда не закрывался
  обычным механизмом сканера ("присваивания закрываются вызовом Init").
  Решение — не переписывать сканер, а добавить один дополнительный `if` в
  уже существующий конце-файла fallback (тот же механизм, который раньше
  использовался только для RTC) — синтезирует блок из накопленных
  присваиваний, с переносом `HAL_DMA_LocalIRQEnable` через механизм
  `pre_init_calls`. `buffer_size_bytes` архитектурно всегда unresolved —
  реальное значение передаётся аргументом `Len` в `HAL_DMA_Start(...)`
  (C-выражение типа `sizeof(x) - 1`, не литерал присваивания — сканер его
  не разбирает). Глобальный `DMA_InitTypeDef` не имеет JSON-представления в
  конфигураторе вообще — пропускается диспетчером с поясняющей note, а не
  маппится.

HW-уровня здесь нет (чистый парсер, см. преамбулу раздела выше) — факт
закрытости не требует проверки на плате, она относится только к forward-
кодогену этих четырёх периферий (остаётся открытым, см. таблицу Тир 2 выше).

## Рекомендация по порядку фиксов

Порядок по возрастанию риска/стоимости:
1. **Тир 1** — расширение уже работающих пайплайнов (I2C/Timer16/Timer32/SPI/Clock)
   — наименьший риск, модули уже валидированы на железе хотя бы частично.
2. **Тир 2** — новые модули с готовым HAL (RTC/CRC/EEPROM/WDT/DAC/ADC/CRYPTO/OTP/TSENS)
   — стандартный паттерн (schema+parser+codegen+GUI-узел) уже отработан 5 раз.
3. **Тир 3** — регистровая работа без HAL (Boot Manager/режимы питания/PVD/Bus Watchdog)
   — отдельное проектирование регистровых структур, выше риск ошибки, сложнее
   HW-валидировать (часть — аналоговые пороги, которые без специального
   оборудования не проверить).

Каждый пункт из Тир 1/2/3 при реализации проходит через обязательный
hardware-validation gate ([[feedback_hardware_validation_gate]]) — ни один пункт
не считается закрытым до проверки на реальной плате осциллографом/логическим
анализатором/мультиметром с указанием конкретной точки пробы.
